## Confirmed findings

### 1. Active-workout “View details” opens nothing

Reproduced manually in the native iOS simulator and local website, in Chromium/WebKit across web/Android/iOS platform modes, and with an Android instrumented test inside the actual WebView. The button is present and clickable but zero dialogs appear. Selection-screen tutorials still work.

Cause: `WebSession` passes the action to `setTutorialExercise`, but the tutorial `Modal` in `Tracker.tsx` is inside the `phase === 'selection'` branch (around lines 1309–1352). The active phase cannot render it.

Recommended fix: mount the tutorial dialog outside the phase branch so both selection and active workouts can use it, preserving exercise state, focus and overlay dismissal. Add an active-phase regression; current tests mainly check library/selection demos and therefore missed this.

### 2. Template dialog actions are obscured by the iOS software keyboard

Observed natively after finishing a one-set workout and opening Save as Template: the input remains visible, but the accessory toolbar crowds/overlaps Save and Cancel falls below the software keyboard. Dismissing the keyboard makes both reachable and saving succeeds. Observed while temporarily using Small text; the original Medium setting was restored afterward.

Cause: shared `Modal.tsx` uses a full fixed-layout backdrop and `90dvh`, without positioning/sizing the portal against `visualViewport.height` and `offsetTop`. Keyboard state on the page frame does not automatically reach the portal.

Comparison: diagnostic Chromium/WebKit geometry tests reproduced obscured Cancel in every platform mode when only the visual viewport shrank from 844px to 500px. All modes passed when the actual layout viewport shrank to 500px. This is a controlled keyboard model, not physical Android/Safari keyboard verification. Android's native manifest uses `adjustResize`; the same Android keyboard defect is **not established**. Mobile Safari with visual-only keyboard resizing shares the susceptible code and needs real-device confirmation. Desktop has no equivalent software-keyboard issue.

Recommended fix: anchor the modal to the visible viewport and keep its actions reachable through scrolling or an action area. Check save/edit/delete forms with software keyboards, large text and long content.
